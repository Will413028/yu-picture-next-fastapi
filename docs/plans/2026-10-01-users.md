## Session 與 CSRF 契約

- DB auth_sessions 儲存 SHA-256 opaque token digest、nullable user_id、created_at、last_seen_at；cookie只存隨機256-bit token、HttpOnly、SameSite=Lax、Path=/。非 local 預設 Secure；Make/test 顯式 local mode 才允許HTTP。
- GET /auth/csrf 建立／沿用匿名或已登入 session，回傳 csrf_token（以 opaque cookie token 派生 HMAC），no-store；CSRF值不存 localStorage。
- unsafe requests 一律要求明確允許的 Origin 與 X-CSRF-Token；包括register/login，避免 login CSRF。沒有 CORS broad allow。
- idle30分鐘、absolute24小時；DB server-side 驗證。登入輪替目前session；登出刪除目前session；改role／soft delete撤銷目標user全部session；會員兌換撤銷該user舊sessions並發新cookie。每次授權重新讀user.role，不信任client或舊session快照。
- session建立與 user/business 更新在同一 DB transaction。回應只含白名單欄位，401未登入、403權限/CSRF錯誤、404不存在、409帳號/兌換衝突、422輸入不合規。
- Next.js catch-all `/api/` 只做固定upstream HTTP transport，轉交Cookie/Origin/CSRF與Set-Cookie；業務与權限都在FastAPI。Browser只呼叫同源API；SSR需要本人時才轉交cookie，禁止共享cache。
- 首頁登入狀態由 client /me 呈現；原 readiness SSR保持不變。/account 整合登入、註冊與會員操作，/user/login、/user/register、/user/membership redirect 到對應模式；/admin/users、/users/[id] 提供管理與公開profile；無權限admin API/UI皆拒絕。
- 所有POST前，client現取GET /auth/csrf，不cache token；登入／會員cookie輪替後下一次unsafe request取得新token；登出後先重新建立匿名session。舊token配新cookie必須403。

## HTTP payload 白名單

- register：account 4–256、password/confirm_password 8–128，非空白、確認一致、extra forbid；201只回id，不自動登入。
- login：account/password同上述界線；200回本人視圖並Set-Cookie輪替。GET me回同視圖：id/name/avatar/profile/created_at/account/role/edited_at/updated_at/vip_expires_at/vip_number；所有ID string。回應不含hash/code/session token。
- admin create：account/password必填，name預設無名、avatar/profile nullable，role預設user；201回安全本人視圖。
- admin patch：只允許name/avatar/profile/role；省略不變，avatar/profile的null清除，name/role的null拒絕；200回安全視圖。get/list同視圖；delete204。
- redemption：code 1–128非空，200安全本人視圖＋輪替cookie。GETcsrf回csrf_token＋必要時Set-Cookie；logout204刪cookie。
- Pydantic validation response不能回顯input，避免回應重複password/code；422只回安全訊息。
- DB transaction dependency使用function scope，commit成功後才發response與Set-Cookie。

計畫審查2項已修：request/response界線與null語意、CSRF輪替後銜接；驗收加入「登入→兌換→登出→再次登入」與舊token拒絕。

## 會員原子性

- vip_codes：digest唯一，used_by、used_at nullable；原code不落DB。CLI讀隱藏輸入後只存digest。
- 兌換SELECT code FOR UPDATE；同 transaction 更新used flag/user期限/role/session rotation；任何一步失敗全rollback。使用者行也加鎖，避免同人併發用兩碼造成session/期限互相覆蓋。
- 月份加12採日曆年規則，2/29落到次年2/28；來源也是offsetMonth12。
- 到期欄位在本階段展示；原來源未實作自動role降級，不自行新增expiry job。後續若需變會員業務另提決定。

## 實作順序與驗收

1. migration 0002 users/sessions/vip_codes、ORM、Argon2id、session/CSRF與typed responses；安裝新增Argon2依賴需下載授權。FastAPI minimum 使用本階段已驗證的0.142.2，避免function-scope Depends落到未驗證的舊版。
2. REST、CLI、proxy與頁面；補上端到端表單、admin搜尋/編輯/刪除與公開profile。
3. `make migrate lint-api test-api`：真實PG隔離schema；註冊欄位/未知role拒絕、唯一性並發、case/accent matching、Argon2 salt、錯密碼、cookie屬性、session輪替／idle/absolute／登出、CSRF缺失/錯誤Origin、角色即時變更／撤銷、soft delete、公開欄位不洩漏、排序白名單。
4. 會員測試：兩人同碼只成功一次、失敗不消耗碼、原規則now+12 months/role=vip、2/29、重複兌換、same user併發；不讀真實code檔或建立真實使用者credential。
5. `make check`：保留原skeleton驗收，加 browser register/login/me/logout、會員兌換（API fixture準備合成code）、admin普通用戶拒絕／admin完整CRUD。Synthetic credentials僅測試記憶體使用，不出現在log或shared wiki。
6. mutation：移除admin gate必須使403 regression失敗；提前commit兌換flag後注入更新失敗，rollback regression必須失敗。只在隔離schema、process內patch，不修改共享程式碼／dev資料。
7. fresh plan/code/design reviews、文件對帳、typecheck/build、桌機／手機QA。驗收真的通過才勾上層步驟2。

消費端搜尋：`rg -n 'userController|exchangeVip|getLoginUser' <reference>/yu-picture-frontend/src`；新介面消費端 `rg -n 'auth/|admin/users|membership|csrf|session' api/app web/src api/tests web/tests`。

停止條件：來源或使用者會員決定不同、secret/外部下載未授權、任何測試失敗；只可操作本專案DB。無新provider／正式環境。新非業務安全表為本階段session與原子code更新所必需。

回滾：新本機環境，保留dev volume；migration downgrade需要先明確同意移除該階段新users資料，不自動執行。CI/test schema是測試自己建立的，僅移除有明確prefix且本test拥有的schema。

延後：正式部署前（上層步驟7）需加驗證登入／兌換rate limit與session清理排程、HTTPS/domain/Secure配置；現在不宣稱production-ready。與圖片/空間相關的權限仍在後續階段。
